## Behavior and ownership

**Wiki entry:** the confirmed News graph instrument takes precedence on every entry. A remembered Wiki is restored only when no applicable graph stock exists or its stock matches. A matching news DB without a Wiki is preselected for creation; opening a page does not start model work. Search-input drafts are not confirmed graph identity. Explicit Wiki selection remains available within the page, and stale requests cannot overwrite a newer stock.

**Preparation:** a persisted root forest contains a content fingerprint of all source rows, channel definitions, stock identity, date range, source separation, relation and exploration settings, and algorithm/cache version. Only an exact match reuses its tree membership; modified news, dates or rules rebuild it. Coverage and pending work are still evaluated against current extractions. First-time preparation is not skipped. Enqueue reads the large configuration once, rather than repeatedly decoding it for each field. The UI shows the current preparation stage and elapsed seconds; it makes no percentage/ETA or constant-speed claim.

**Chat:** `chat/history.mjs` stores application transcripts and internal SDK thread references in `data/private/chat-history.json` (0600, parent 0700). A random browser-owner capability stays in that origin/profile's localStorage and never enters workspace snapshots, graph exports or the UI. News and Wiki histories remain distinct. Authenticated session routes list, reopen and delete only that owner's conversations; thread IDs are never accepted from the browser or returned to it. The same origin/profile survives refresh and service restart; other devices/profiles do not automatically share histories. Web Locks serialize first-owner creation across same-origin tabs when supported.

New chat retains earlier conversations. Opening history restores exact stored text and resumes its SDK thread on the next explicit message; current browser context still controls the new turn. Concurrent turns/open/delete on the same conversation are rejected while replying. User and assistant messages persist as received; an uncompleted model turn is never automatically replayed. Limits are 200 conversations per owner and 2,000 messages per conversation, with explicit errors instead of silent pruning.

Delete requires a UI confirmation and removes the application's stored record, invalidating idle session references. It does **not** erase separate SDK/provider retention records. No pre-feature in-memory transcripts can be reconstructed. Existing access controls still apply to all new routes; the history-owner capability adds isolation within those boundaries.
